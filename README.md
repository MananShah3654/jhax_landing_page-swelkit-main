# JHAX.ai Landing Page — SvelteKit (static / serverless)

A **static** SvelteKit port of the original FastAPI + React JHAX.ai landing page.
There is **no backend server and no SQL database** — the only server-side code is a
single Cloud Function that resolves Google Maps short links (see below):

- **Free Audit** calls Google Places **from the browser** (Maps JavaScript API
  Places library) and runs the "What JHAX Found" heuristics **client-side** — same
  cards, same numbers as before.
- **Leads** (both forms) are written straight to **Firebase Firestore** from the
  browser (project `jhax-coo`).
- **Maps links** pasted into the audit form are resolved by a Cloud Function
  (`resolveMapsLink`).
- **Teaser findings** are generated by a second Cloud Function (`auditFindings`),
  which calls Google Gemini server-side and verifies every claim before returning it.

The build output in `build/` is plain static files — host it anywhere.

## Run

```bash
npm install
cp .env.example .env      # fill PUBLIC_* values (see below)
npm run dev               # http://localhost:5173
npm run build             # -> ./build (static SPA)
npm run preview           # serve the static build locally
npm run check             # svelte-check (0 errors, 0 warnings)
npm run parity            # heuristics still byte-identical to the original Python
```

## Environment (all `PUBLIC_`, inlined into the browser bundle)

```
PUBLIC_AUDIT_DATA_SOURCE=google        # "osm" no longer runs an audit - see below
PUBLIC_GOOGLE_PLACES_API_KEY=...        # Maps JS API + Places API (New), referrer-restricted
PUBLIC_FIREBASE_API_KEY=...
PUBLIC_FIREBASE_AUTH_DOMAIN=jhax-coo.firebaseapp.com
PUBLIC_FIREBASE_PROJECT_ID=jhax-coo
PUBLIC_FIREBASE_APP_ID=...
```

> **`osm` is no longer a working data source.** OpenStreetMap has no ratings and no
> reviews, and the provider used to fill that gap with `seededMetrics()` — a
> SHA-256 hash turned into a plausible-looking rating and review count. Those
> numbers looked completely real, which is what made them dangerous. The provider
> now **refuses with a clear error** instead of fabricating. `seeded.js` is kept
> only because the parity harness still covers it; nothing in the audit path calls
> it.

## One-time cloud setup

**Google Places key** (Google Cloud console): enable **Maps JavaScript API** +
**Places API (New)** on the key, then restrict it to your site's HTTP referrers.
(Places REST endpoints don't allow browser CORS — that's why we use the Maps JS
library.)

**Firestore** (Firebase console → project `jhax-coo`):
1. Firestore Database → **Create database** (Production mode).
2. Deploy the security rules in `firestore.rules`:
   ```bash
   firebase deploy --only firestore:rules
   ```
   Rules: the `leads` collection is **write-only** for clients (no read/update/
   delete), with required-field validation to block empty/spam submissions.

## Google Maps link resolver (the one Cloud Function)

The audit form takes either a **restaurant name + city** or a **pasted Google Maps
link**. Long links (`google.com/maps/place/…`) carry the place name in the URL and
are parsed **in the browser** — no network call. Short links
(`maps.app.goo.gl/…`) are opaque redirects whose target sends **no CORS headers**,
so the browser cannot follow them; a Cloud Function does it instead.

```
browser  ->  /api/resolve-maps-link?url=…  ->  { name, city }  ->  normal audit
```

One implementation, mounted twice — `src/lib/server/resolveMapsLink.js`:

| Where | How |
|---|---|
| `npm run dev` | Vite middleware (`vite.config.js`) — nothing extra to run |
| deployed | Cloud Function in `functions/`, same path via the `firebase.json` rewrite |

`functions/shared/` is **generated** — `scripts/sync-functions-shared.mjs` copies the
source files in as a `predeploy` hook, so the two never drift. Never edit it by hand;
edit `src/lib/` and run `npm run sync:functions`.

**Deploying the function needs the Blaze (pay-as-you-go) plan** — Cloud Functions are
not available on Spark. If you stay on Spark, everything else still works: long Maps
links parse client-side, and short links show an inline "type the name instead"
message rather than breaking the page.

```bash
cd functions && npm install && cd ..   # one time
firebase deploy --only functions,hosting
```

## Teaser findings (`auditFindings`)

The free teaser must say something specific and TRUE about the visitor's own
restaurant — never generic advice. Findings are written by Gemini
(`gemini-3.6-flash`) from the Places payload, server-side so the API key stays off the
client.

A prompt alone is not a guarantee, so there are two independent defences in
`src/lib/server/auditFindings.js`:

1. **Constrained input.** `buildPayload()` decides exactly what the model may see.
   The system prompt forbids outside knowledge, generic advice, invented numbers,
   and — because Places returns at most **5 reviews** — any claim about customers
   in general.
2. **`verifyFindings()` — the gate.** After generation, every finding's `evidence`
   string is re-checked against the payload. A review quote must appear verbatim in
   a real review; a figure must match a real figure. Anything that cannot be traced
   back is **dropped before it reaches the browser**. The model is treated as
   untrusted.

The evidence that survived is shown to the user under each finding, so the claim
and its receipt travel together.

**Setup.** The function needs a Gemini key in Secret Manager:

```bash
firebase functions:secrets:set GEMINI_API_KEY
```

Locally, put `GEMINI_API_KEY` in `.env` — `vite.config.js` copies it into
`process.env` for the dev middleware, since Vite itself only exposes `PUBLIC_`/
`VITE_` vars and only to the browser. A real shell variable takes precedence.
With no key set the endpoint returns **503** and the teaser still renders: the
score, sub-scores and listing data are unaffected, and only the findings panel
degrades.

The model is pinned to `gemini-3.6-flash`; override it with `GEMINI_MODEL` in
`.env` without touching code.

## How the teaser streams

`runAudit()` emits four waves instead of resolving once at the end, so the page
fills in rather than sitting behind one spinner:

| Wave | Contains | Typical timing |
|---|---|---|
| `place` | name, address, photo | ~0.8s (Places `searchText`) |
| `scores` | overall health + 4 sub-scores | same tick — computed locally |
| `competitors` | local rank against nearby restaurants | ~1s (Places `searchNearby`) |
| `findings` | the grounded prose | seconds later (Gemini round-trip) |

The progress list ticks off each wave **when its event actually arrives** — it is
not a timed animation.

### Sub-scores

Four dimensions in `src/lib/audit/subscores.js`, all computed from Places data
only. A dimension with no data renders as —, never a guess:

| Sub-score | Derived from |
|---|---|
| Reputation | star rating on the 2.5–5.0 band |
| Visibility | review volume, log-scaled (1,000 reviews = 100) |
| Freshness | age of the newest review Google returned, over a 180-day window |
| Listing | presence of hours, website, photos, description (25 each) |

The **overall** score stays `estimateHealthScore()` in `heuristics.js` — unchanged
and still locked to the original Python by `npm run parity`. Sub-scores sit
alongside it as a breakdown, they do not feed into it.

### Local rank

`src/lib/audit/competitors.js` answers the question an owner actually cares about:
**where do I sit against the places a diner picks instead of me?** One extra Places
call (`searchNearby`, started the moment the place is known and raced against the
Gemini round-trip) returns up to 20 nearby restaurants; the ranking itself is pure
arithmetic on real Google ratings.

Rules that keep the rank defensible:

| Rule | Why |
|---|---|
| Rivals need **20+ reviews** (`MIN_COMPETITOR_REVIEWS`) | Without a floor the board is decided by noise — a 5.0★ place with four reviews would outrank a genuinely good restaurant with nine hundred |
| Needs **2+ comparable rivals** | Below that a "rank" is a coin toss, so the module refuses |
| No subject rating → **refuse** | There is no position to report on the only axis this ranks by |
| Subject excluded by place **id**, name as fallback | Otherwise a restaurant is ranked against itself and reads as #2 on its own street |
| Sorted by rating, then review count, then name | 4.3★ over 800 reviews is not the same as 4.3★ over 40, and identical inputs must always produce an identical board |
| `includedTypes`, **not** `includedPrimaryTypes` | A place whose primary type is `indian_restaurant` does not match a *primary*-type filter of `restaurant`, which would silently drop most of the street |

A refusal is a value (`{ ok: false, reason }`), never an exception — the panel simply
does not appear, and the audit around it is unaffected. The basis line says "the N
most prominent nearby restaurants" because that is what Nearby Search returns: up to
20 places by prominence, not a census of the radius.

The panel is **free and fully visible** — it is the part an owner leans in for, and
the data is browser-side anyway, so locking it would be theatre rather than a gate.
It is rendered into the PDF from the same `rankRows()` helper the page uses, so the
downloaded report shows exactly the board that was on screen.

### The PDF report

`src/lib/pdf/auditReport.js` draws the report with **jsPDF vector primitives**. It
used to go through html2canvas — the whole report became one tall PNG that was then
sliced across pages, which meant a document that blurred the moment anyone zoomed,
could not be selected or searched, weighed hundreds of KB, and happily cut a line of
text in half at a page boundary. The rewrite fixes all four: **~11 KB, real text,
sharp at any zoom.** `html2pdf.js` is gone from the dependencies; jsPDF is imported
lazily so it only reaches visitors who actually download something.

Layout rules worth knowing before editing it:

- Every block **measures itself before it draws** (`room(h)`), so a section moves to
  the next page whole instead of being sliced. `section(title, firstBlockH)` reserves
  the heading together with its first block, so a heading is never orphaned at the
  foot of a page.
- **Standard PDF fonts are WinAnsi-encoded.** Hand jsPDF one character outside that
  set and it silently switches the ENTIRE string to two-byte encoding, which renders
  as garbage — a single stray glyph corrupts the whole line. `safe()` maps or drops
  those characters on the way in: the rupee sign becomes `Rs `, and **stars are drawn
  as vector polygons** rather than typed. If you add copy to this file, run it through
  `safe()` (every helper already does) and never assume a symbol will survive.

### What the teaser locks, and how

`applyTeaserPolicy()` in `auditFindings.js` stamps a **`teaser_visible`** flag on
every finding and every sub-score. The client renders purely from that flag — the
markup contains no rule about which fields are free — so the free/paid line moves by
editing `TEASER_POLICY` alone. A missing flag is treated as locked, so an item whose
flag has not arrived yet fails closed.

Locked rows are **redacted server-side, not hidden in CSS**. A locked finding keeps
its `kind`, `severity` and short `label` and loses `title`, `body` and `evidence`
entirely — that text is never in the DOM, so it cannot be read out of devtools. The
same goes for a locked sub-score's number.

What a locked row still shows, on purpose:

| | Locked | Unlocked |
|---|---|---|
| Finding | severity icon + colour, tier label, factual `label` ("No website linked"), skeleton bars | adds title, body, and the verified evidence quote |
| Sub-score | dimension name, lock icon, hatched bar | adds the 0–100 value, coloured bar, and basis |

The `label` on a locked finding is checked by `verifyFindings()` like every other
claim — it must carry no ungrounded number, and `severity` must agree with `kind` —
so a locked row is accurate even though its detail is withheld.

Because locked text is never sent, signing up triggers `unlockAudit()`, a second
request with `signed_up: true`, before the PDF is built. That is the deliberate cost
of keeping withheld content out of the browser.

> `signed_up` is asserted by the client, matching the existing localStorage signup
> gate. This is a product gate, not an authorization boundary — it is exactly as
> strong as the download gate that already shipped.

## Deploy (static hosting + one function)

`build/` is plain static files, so any host works (Netlify, Vercel, GitHub Pages,
Cloud Storage, S3, …) — serve it with an SPA fallback to `index.html`. On a host
other than Firebase you also need to route `/api/resolve-maps-link` to that host's
own function runtime (the handler is `handleResolveRequest` in
`src/lib/server/resolveMapsLink.js`); without it, only short Maps links degrade.

**Firebase Hosting** (same `jhax-coo` project, one command set):
```bash
npm run build
firebase login
firebase deploy --only hosting,functions,firestore:rules
```
`firebase.json` already points hosting at `build/` with the SPA rewrite, and
`.firebaserc` targets `jhax-coo`.

## Data model — Firestore `leads`

Same fields the old `/api/leads` stored (nothing dropped):
`email`, `source`, `business_name`, `person_name`, `phone`, `created_at`
(`created_at` = Firestore server timestamp). `source` is `final_cta` (footer form)
or `audit_report_download` (audit PDF gate).
